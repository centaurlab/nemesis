# Nemesis verification report contract

Nemesis writes schema-validated JSON reports to `.nemesis/reports/`. The current `schemaVersion` is `1.0.0`. Examples generated by real execution are `demo/sample-initial-report.json` and `demo/sample-strengthened-report.json`.

## Top-level fields

- `id`, `createdAt`, `schemaVersion`: run identity, real ISO timestamp, and contract version.
- `repo`: materialized repository path, base and candidate refs, exact candidate SHA, and production-only fingerprint.
- `task.exactText`: the unmodified developer request.
- `baseline`: outcomes of two complete true-implementation runs, total/stable test counts, and excluded flaky test identities.
- `requirements`: the primary product result. Each entry preserves the requirement ID, normalized text, exact source quote, verdict, and its executed counterfactual evidence.
- `summary`: requirement totals plus independent build, test, and proof states.
- `executionTrace`: actual ordered engine events. A trace event has an ISO timestamp, stage, optional requirement/counterfactual IDs, message, and `RUNNING | PASS | FAIL | INFO` status.
- `metadata`: verifier/provider versions and challenge cache identity.

## Requirement verdicts

`DEFENDED` means at least one valid challenge existed and every valid challenge was killed by stable relevant tests. `NOT_DEFENDED` means at least one valid challenge survived. `UNVERIFIED` means no valid executable challenge existed.

Each counterfactual records:

- `validity`: `VALID` or `INVALID`;
- `invalidReason` when execution could not support scoring;
- `score`: `KILLED`, `SURVIVED`, or `INVALID`;
- the executable witness scenario and both expected observations;
- `witness.confirmed`, which is true only after the same harness demonstrates expected behavior on the true implementation and differing behavior on the adversarial implementation;
- stable relevant and unrelated test identities actually run;
- `killedByTests` for a killed challenge;
- diagnostics for the distinct `witness-failed-on-true-implementation` path. `possibleImplementationViolation` is deliberately hedged and never means “proven bug.”

## Summary semantics

- `build`: candidate typecheck and deterministic boot result.
- `tests`: both full baseline suites passed.
- `proof`: `PASS` only when all requirements are defended, `FAIL` when a valid challenge survives, and `UNVERIFIED` when any requirement has no valid challenge.

There is intentionally no mutation score. A cached challenge is only a reusable source artifact; every report contains fresh compile, boot, regression, witness, relevant-test, and scoring execution.
